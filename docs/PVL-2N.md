# PVL-2N — Single-Run Solver-Execution Gate

Status: implementation candidate

## Objective

PVL-2N introduces the first explicit transition from an immutable PVL-2M experiment package toward solver execution. The unit deliberately gates **one selected planned run only**. It preserves the package and run fingerprints, records preflight and tool/environment provenance, and refuses to substitute preview geometry for a solver-ready Rig model.

PVL-2N does not yet claim a full Rig FEM solve. The current Rig geometry architecture has a solver-neutral/preview representation, but no constructive solver geometry adapter for the physical steel frame, isolated copper boundary, chamber, and coils. Active FEM routes therefore remain blocked until that missing ordinary-physics dependency is implemented and validated.

## Immutable source package

The source PVL-2M package remains unchanged. Before any gate decision is accepted, PVL-2N verifies:

- the complete PVL-2M checksum set;
- `package_manifest.json` structure;
- experiment configuration and physics-state hashes;
- run count and ordered run IDs;
- deterministic plan hash against `run_matrix.json`;
- deterministic package fingerprint;
- the selected run's configuration and physics-state hashes;
- the selected run manifest's Rig and material-library fingerprints.

Any failure blocks the operation before an execution overlay is created.

## Deliberate single-run selection

The API requires all of:

- `experiment_id`;
- `package_id`;
- `run_id`;
- the current `RigV1Schema`;
- `single_run_confirmation=true`.

There is no batch-execution endpoint. Every persisted gate manifest hard-codes:

- `single_run_only=true`;
- `batch_execution=false`;
- `biological_testing=false`.

## Preflight and solver routing

The selected run is reconstructed from the immutable experiment configuration plus its exact Coil A/B states from the stored run matrix. Existing orchestrator preflight then verifies Rig/material fingerprints, required geometry measurements, material references, sample medium, solver fidelity, and solver route.

Routes remain:

- all coils off → `control`;
- DC-only active coils → `magnetostatic`;
- common-frequency harmonic coils → `magnetoquasistatic`;
- mixed or unsupported excitation → blocked by preflight.

A control run may pass the gate because no FEM solve is required. It still records `solver_execution=false`.

## Constructive-geometry execution block

For `magnetostatic` and `magnetoquasistatic` routes PVL-2N currently records:

`constructive_solver_geometry_unavailable`

This is intentional. The existing frontend/preview geometry must not be silently promoted to a FEM geometry, and the validated POC-005 surrogate geometry must not be presented as the physical Rig. Active-run execution therefore remains `execution_allowed=false` and `solver_execution=false` until a solver-ready constructive Rig adapter exists.

This block protects the project boundary established by PVL-2D: illustrative or display geometry is not equivalent to measured hardware topology.

## Execution overlay

Gate evidence is written outside the immutable experiment package at:

`results/<experiment_id>/executions/<package_id>/<run_id>/<job_id>/`

Each gate directory contains:

- `job_manifest.json` — package/run fingerprints, solver route, preflight state, execution decision, issues, tool versions, and safety flags;
- `environment.json` — UTC capture time, Python/platform metadata, architecture, and Gmsh/GetDP versions when available;
- `checksums.json` — SHA-256 checksums for persisted gate files;
- `raw/` — empty reserved directory for a future permitted single-run execution.

No mesh, GetDP input, field result, metric, thermal result, or solver log is generated by PVL-2N.

The gate is staged and renamed atomically. An existing deterministic gate identity is never overwritten.

## API

`POST /api/v1/experiment/execution/single/gate`

The server derives the package location from its configured results root. Requests cannot supply arbitrary filesystem paths.

Expected outcomes:

- HTTP 200 — auditable gate decision, which may be allowed for a no-solver control or blocked for an active FEM run;
- HTTP 404 — package or selected planned run does not exist;
- HTTP 409 — package integrity failure or deterministic gate record already exists;
- HTTP 422 — invalid request, including omission of explicit single-run confirmation.

## Validation gate

PVL-2N must demonstrate:

- active DC runs route to magnetostatic preflight but remain blocked without constructive solver geometry;
- OFF/OFF controls can pass without claiming solver execution;
- package tampering blocks the gate;
- unknown runs are rejected;
- Rig-fingerprint mismatches remain visible as preflight failures;
- single-run confirmation is mandatory at the API boundary;
- gate records are deterministic and non-overwriting;
- the immutable PVL-2M package still passes checksum verification after a gate record is persisted;
- no solver artifacts are created while execution is blocked;
- all existing Python/API/frontend and POC-001 through POC-005 regressions remain green.

## Scientific boundary

PVL-2N adds execution provenance and a hard ordinary-physics dependency gate. It does not add a Portal Hypothesis term, anomaly classifier, biological test, or spacetime interpretation. A blocked run is not a failed physics result; it means the software refuses to produce a result from geometry it cannot justify.

## Next unit

PVL-2O should implement and validate the first solver-ready constructive Rig geometry adapter for **exploratory simulation only**, using explicitly provenance-tagged dimensions and maintaining a hard distinction from hardware-fidelity geometry. Only after that adapter passes topology, mesh-quality, convergence, and POC regression checks should PVL-2N be extended from gate-only behavior to atomic single-run FEM execution.
